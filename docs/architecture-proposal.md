# Architecture proposal

## Recommendation

Use a **file-per-entity canonical store** under **.pman/**: UTF-8 JSON for structured records and Markdown for long-form plans/specifications/decisions. Treat the store as a graph projected from explicit IDs. Build a public TypeScript library as the core and a thin **pman** CLI as its consumer.

Canonical .pman plan files are inside the project and Git-tracked by default; initialization must not add them to .gitignore. A clean clone contains the goals, tickets, decisions, comments, metadata, and relationships that agents need to inspect and edit offline. SQLite, servers, accounts, Git remotes, and MCP are not required. Add a rebuildable local cache only if profiling justifies it; it must never be authoritative or required to read/edit plan data. Only generated caches and ephemeral sessions, process locks, and run logs are excluded from canonical Git-tracked state.

## Storage options

Scores: 1 weak, 5 strong for Git-native use. Merge score describes likely ordinary Git behavior, not conflict-free semantics.

| Option | Readability | Git merge | Query/scale | Unlimited nesting | Complexity | Decision |
|---|---:|---:|---:|---:|---:|---|
| One large JSON/YAML/JSONL file | 3 | 1 | 3 | 5 | 4 | Reject canonical: updates share a conflict hotspot; concurrent appends/edits need custom reconciliation. |
| One file per entity, explicit links | 4 | 5 | 3 | 5 | 4 | **Recommend.** Changes are focused; stable IDs survive moves; validate graph integrity. |
| Parent encoded in nested directories | 4 | 2 | 2 | 2 | 3 | Reject as relationship model: reparenting renames subtrees and confuses physical path with semantics. |
| SQLite in repository | 2 | 1 | 5 | 5 | 2 | Reject canonical MVP: binary conflicts, locks and opaque diffs. |
| Hosted/self-hosted database | 1 | 3 | 5 | 5 | 1 | Reject as required system: accounts, availability, backups and service assumptions. |

## Proposed layout

    .pman/
      config.json
      schema.json
      goals/<id>.md
      plans/<id>.md
      decisions/<id>.md
      tickets/<first-two-id-chars>/<ticket-id>.json
      comments/<first-two-id-chars>/<comment-id>.json
      relationships/<first-two-id-chars>/<relationship-id>.json
      assets/                 # optional later, user-managed

All files under .pman that form canonical project state are meant to be committed with the repository; pman does not automatically ignore them. References use normalized repository-relative forward-slash paths and are checked to remain in the repository. IDs are immutable; filenames derive from IDs, never titles/parents. A future local cache is ignored by default and keyed by schema version and canonical hashes. It is disposable. Credentials, remote sessions, agent stdout and locks are not tracked.

## Core entities

Each structured record has schemaVersion and stable id. Canonical JSON is UTF-8, LF, deterministically ordered, two-space indented, trailing newline. Publish JSON Schema; reads validate with path/ID diagnostics and never rewrite data.

| Entity | Initial fields |
|---|---|
| Project config | schema version, project ID/name, ordered project statuses (default: todo, in_progress, done, cancelled) and custom properties, context/output limits. |
| Goal | ID, title, Markdown body, status, timestamps, optional parent goal and ticket/plan links. |
| Plan/spec/decision | ID, kind, title, status, Markdown body, timestamps, explicit links to goals/tickets/decisions. |
| Ticket | ID, title, description, status, priority, labels, properties, nullable parentId, timestamps, optional owner/estimate. |
| Comment | ID, ticketId, body, author label, timestamp, optional edit/delete markers. Separate records reduce ticket rewrites. |
| Relationship | ID, source, target, type and timestamp. Types: blocks, relates_to, duplicates, implements, validates, supersedes, document reference. |
| Context reference | Typed repo path, symbol/path hint, URL or entity ID; rationale and optional line range. |
| Activity event | Optional later per-entity records. Git history is initial audit trail; no global append-only file. |

Use UUIDv7 IDs generated by Node crypto, as confirmed by the product owner. Parentage is metadata, not encoded in the ID. Human short IDs are collision-checked aliases; API accepts full IDs.

## Arbitrarily deep tickets

Example record; values are illustrative:

    {
      "schemaVersion": 1,
      "id": "0192f1d0-6a2b-7c00-8c3e-2a49f3d9f200",
      "title": "Add account recovery",
      "status": "in_progress",
      "priority": "high",
      "parentId": "0192f1cf-03ef-7d08-8fc1-91d4e9c00010",
      "createdAt": "2026-10-29T12:00:00.000Z",
      "updatedAt": "2026-10-29T12:30:00.000Z",
      "labels": ["auth"],
      "properties": {},
      "description": "Implement recovery flows."
    }

The same shape represents a root (null parent) or a ticket at any depth. A grandchild references its immediate parent. Creating a child does not rewrite a parent child-array. A directory tree or type label is presentation only.

## Tree and graph rules

- Build ID and parent-to-children indexes in one pass: O(n) time and memory. Traverse iteratively, never with recursive JS calls.
- Sort siblings by stable key, default creation time then full ID. Never depend on filesystem order.
- Subtree query costs O(k) after index construction for k descendants. Page/stream large results and bound default output.
- Parent must exist and be a ticket. Reject self-parent and cycles (iterative reachability check) before writing.
- Validate duplicate IDs, missing parents, self-parenting, parent cycles, invalid status/type, dangling endpoints and blocking dependency cycles. Read-only commands report; repair is explicit.
- Rollups are views: all non-cancelled descendants done -> done; blockers -> blocked; any active descendant -> in_progress; else todo. Show leaf status and derived rollup separately. Do not overwrite child status when a parent changes.
- Dependencies are separate. Blocking edges are acyclic and affect readiness; informational edges may form cycles. Parent-child does not imply blocked-by.
- Design target: 10,000 tickets and a 10,000-deep chain without stack overflow; 100,000 records usable with bounded output and cacheable indexing. These are benchmarks to establish, not measured claims.

## Writes, merges and concurrency

### Local write protocol

1. Resolve repo root and canonical path; reject traversal and unsafe symlink escapes.
2. Read and validate current record; capture revision/content hash.
3. Apply focused patch, preserving unknown extension fields where safe.
4. Write a unique temporary file in the same directory, flush/close, then rename over target. Serialize same-process writes to one path. Test Windows rename, antivirus/indexing, sync folders and network filesystems.
5. Recheck revision before commit; return typed conflict if stale.
6. Use exclusive create for new IDs. Do not use a global activity append file.

Atomic replacement prevents partial reads on common local filesystems; it is not a cross-process or cross-machine lock.

### Git behavior

- Independent entity files normally merge cleanly.
- Creating child changes only the child. Reparenting changes only parentId; validator catches merged orphan/cycle.
- Two updates to one ticket can conflict or be stale. Make conflict visible, reload/reapply manually, and never silently choose a side.
- Duplicate IDs fail validation before normal commands proceed.
- Merged files are canonical. Cache is disposable. Branch-local execution records are excluded.
- A future optional coordination service may offer leases/claims/notifications but never changes file format or becomes required.

Git linked worktrees support concurrent checkouts but are not a conflict-free synchronization service. See the [Git worktree manual](https://git-scm.com/docs/git-worktree).

## TypeScript API boundaries

- **Core:** types, schema/migrations, adapter interface, tree/dependency algorithms, search/context, canonical serialization; no CLI side effects.
- **Node adapter:** filesystem, atomic writes, root detection, path safety, using built-ins.
- **CLI:** argument parsing, output and exit codes on top of core.
- **Optional future MCP adapter:** translates protocol calls to core API; no separate business rules.

API proposal:

    import { openProject } from "@mmilad/pm";

    const project = await openProject({ cwd: process.cwd() });
    const ticket = await project.tickets.get(ticketId);
    const children = await project.tickets.children(ticket.id);
    await project.tickets.reparent(ticket.id, { parentId: nextParentId });

Expose async methods, typed errors (NotFound, ValidationError, CycleError, ConflictError, UnsupportedSchemaVersion, StorageError), injectable storage for tests, and narrow semver-governed exports.

## CLI proposal

| Command | Purpose |
|---|---|
| pman init [--yes] | Create .pman without overwriting existing data. |
| pman goal/plan/decision create | Create planning artifacts. |
| pman ticket create --title ... [--parent ID] | Create at any depth. |
| pman ticket show/list/update/move | Inspect, filter, edit and reparent. |
| pman tree [ID] [--max-depth N] [--format json] | Bounded display; max depth affects output only. |
| pman relation add/remove/list | Manage typed edges. |
| pman context ID [--budget N] [--format json] | Deterministic packet with provenance. |
| pman search QUERY [--format json] | Offline full-text search. |
| pman serve [--open] [--port N] | Serve a browser UI for only the current project on loopback; run in the foreground. |
| pman validate | Check schemas, IDs, links, cycles, paths and values. |
| pman doctor | Read-only diagnostics; repair is explicit. |

Commands support human and JSON output, noninteractive operation, stable exit codes, stdin/file input, explicit field flags, Unicode/path safety and completions. A repo devDependency with lockfile is the reliable install. One-shot package-manager use is convenience; avoid downloading unpinned latest code in sensitive/offline workflows.

## Project-scoped local web UI

`pman serve` is an optional local interface over the same core API and canonical `.pman/` files. Resolve exactly one initialized project from the current working directory (or nearest ancestor); refuse to start if no project is found. Do not enumerate other projects, consult a global registry, expose a project picker, or create a shared multi-project service. The UI provides a navigable ticket tree and detail/edit views, planning documents, and local search/context; supported writes use the same validators and storage adapter as CLI commands.

Run as a foreground process and print the URL. By default bind only to `127.0.0.1:4000`; if that port is occupied, fail clearly instead of selecting a random port or starting another instance. An explicit `--port` override may be used and must print the actual URL. `--open` may launch the browser only after a successful bind. Stop with Ctrl-C. No account or auth flow is required because the service is local to the machine and project. Do not provide a LAN bind option in the MVP.

No-auth local service still needs browser protections: reject unexpected Host values, reject cross-origin state-changing requests using Origin checks and CSRF protections, disable CORS, and serve assets locally without third-party scripts. Do not execute project extensions, hooks, or ticket instructions. The CLI/API and offline project files must remain fully usable when the UI server is stopped.

## npm and platform constraints

Use ordinary Node.js JS/TS files, npm bin mapping for pman and public exports. npm documents platform command shims including Windows .cmd and the Node shebang. Keep OS/CPU unrestricted absent a verified reason. Choose a supported Node LTS minimum at implementation start and test it. Avoid native dependencies, shell-specific installers, WSL, global installation and OS-specific DB binaries. Use Node built-ins where feasible. Test paths with spaces, Unicode, drive roots, UNC paths, case differences and both separators. Check package and command names before release.

Sources: [npm package.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/) and [Node release schedule](https://nodejs.org/en/about/previous-releases).

## Search and context

Search scans canonical records and Markdown locally and deterministically. Return entity ID, title, matched snippet and repo-relative source. Build in-memory indexes first; persist ignored rebuildable indexes only after profiling. No remote calls/embeddings.

Context packet sections: ticket, ancestry, bounded descendants, blocking edges, linked plans/decisions, relevant comments and referenced repo files. Include reason and source path for every selection; stable sorting, byte/token budget and omitted counts. Do not execute ticket instructions. Avoid opaque hot-file rankings; local search yields matches, not authority.

## Versioning and migration

- Every record declares schemaVersion; config declares store version.
- Support current and prior version during early development; never migrate on read.
- Migration command previews changes, then writes using a documented backup/Git checkpoint policy.
- Preserve unknown fields when possible.
- Migrations are pure, deterministic, idempotent transformations with fixtures.
- Validation works offline and reports exact paths/IDs.

## Risks

1. Deep-tree handling: recursion in traversal/render/rollup silently caps depth; mandate iterative operations and stress benchmarks.
2. Git conflicts: separate files lower unrelated collisions but do not semantically merge same-record edits.
3. Record sprawl: shard and paginate; optimize only from benchmarks.
4. Platform filesystems: rename, symlinks, Unicode and case differ; test on Windows early.
5. Schema drift: external editors may alter files; publish schema, preserve unknown fields, migrate explicitly.
6. Instruction injection: plans are untrusted content; separate data parsing from agent policy.
7. Large dependency graphs: use cycle detection and bounded readiness/context results.
8. npm supply chain: check names and publish safeguards before release; no publication in this phase.
9. Local web exposure: enforce loopback binding, Host/Origin checks, no CORS, and no LAN access; no-auth local interfaces still need CSRF defenses.
